# VCarDAS BOOT 刷写输入与工程约定

完整执行链路见[实现方案](implementation.md)。自动回归使用合成固件与模拟 SDK，
首次用于真实台架前，需要验证本机 VCarDAS 的空窗口识别和实际打包、编译、刷写结果。

## 任务输入与设备配置

| ID | 类型 | 内容 |
| --- | --- | --- |
| `CONFIG_PACKAGE` | ZIP 文件 | 同一个 `.das` 工程及其目标目录、CAPL、DLL、打包脚本与工具 |
| `APP_FILE` | 多文件 | 每个目标一组，同名 `.hex` 或 `.cbf` 与 `.rsa` |
| `DRIVER_FILE` | 多文件 | 每个目标一组，同名 `.hex` 与 `.rsa` |
| `VCARDAS_EXE` | 设备文件属性 | 本机 `VCarDAS2.exe` 的完整路径 |

绿色版也必须先在 VCarDAS 的“仿真 → 编译器设置”中配置完整工具链。当前验证版本
要求所选根目录直接包含 `x86_64-pc-linux-gnu`、
`gcc-arm-9.2-2019.12-mingw-w64-i686-aarch64-none-linux-gnu` 和 `mingw64`。
只携带 Windows MinGW 的绿色包会弹出“编译器丢失”并导致 `TestModuleCompile`
失败，这属于 VCarDAS 运行环境不完整，不应通过放宽 SDK 超时绕过。

App 和 Driver 分别成组，不要求两类固件的主名相同。两个目标可以同时加载，文件
选择顺序不决定目标，也不要求包与签名在列表中相邻。App 的同一个主名同时提供
`.hex`、`.cbf` 会形成冲突；Driver 不接受 `.cbf`。

## 工程目录

以下 `FL`、`FR` 都是示例，实际目标名称和数量由目录及输入文件匹配确定。

```text
工程/
  Test.das
  Flash/
    tools/
      cbf2hex.py
      setini.ps1
      sigclean.ps1
      viuver.py
    FL/
      APP/
      Flashdriver/
      capl/FL_flash.can
      DLL/E0X_FLZCU_V0.1.dll
      profile.ini
      put_pkg.cmd
    FR/
      APP/
      Flashdriver/
      capl/FR_flash.can
      DLL/E0X_FRZCU_V0.1.dll
      profile.ini
      put_pkg.cmd
```

目标目录名必须从固件主名开头连续匹配：`FL` 匹配 `FLZCU_...`，不匹配
`XFLZCU_...`。对应 App 文件写入该目标的 `APP`，Driver 文件写入
`Flashdriver`，清除旧刷写文件后再复制本次文件。

文件加载前校验全部目标。没有匹配、前缀同时匹配多个目标、目标缺少配套固件，或
CAPL/DLL 不唯一时，统一报错并要求修正。旧文件清理范围为 `APP`、`Flashdriver`
目录内的 `.hex`、`.cbf`、`.rsa` 文件；未匹配的目标目录不改动。

CAPL 位于目标的 `capl` 目录，`.can` 文件名以目标名开头；DLL 位于 `DLL`
目录，`.dll` 文件名包含目标名。模块名称使用目标目录名。
插件在整棵测试配置树中只清理名称与本次目标相同的 CAPL/XML 模块，包含其他环境中的同名模块；其他名称的模块、环境、文件夹和勾选状态都会保留；多个目标按目录名排序串行执行，
遇到失败停止后续目标。

插件把本次 App 和 Driver 放入任务工程副本内对应目标的 `APP` 与 `Flashdriver`，
从该目标目录运行随工程提供的 `put_pkg.cmd`，并使用工程内的同级 `tools`。
所有目标打包校验通过后，插件将刷写数据复制到 `D:\KUNYI_flash\<目标名>\`，供原样
运行的 CAPL 读取。任务完成后保留该目录中的刷写数据，并将可用报告登记到任务页面。

`.das` 使用任务副本；旧工程由用户先手动处理，插件不自动保存或关闭旧工程。
共享配置保持原样，不再要求并行新建实例。保留的空窗口供插件打开本次工程；软件
未运行时启动指定 EXE。测试结束后关闭执行本次任务的软件。

宿主离线任务会在输入文件名上增加六位序号。插件仅对已知任务快照目录恢复文件名，
匹配与复制使用恢复后的名称，保留用户原文件名本身包含的数字前缀。

## 外部脚本要求

参考 `put_pkg.cmd` 通过 `%~dp0` 进入自身目录，通过 `..\tools` 调用工具，因此
CMD 本身不要求安装在 `D:\KUNYI_flash\`。参考 CAPL 的 `kPkgRoot` 写死了
该绝对路径；用户已确认不能修改 CAPL，因此按给定路径加载刷写数据，不改写脚本。

参考 CMD 的 `pause` 无需为了无人值守运行而修改：宿主 CLI 在写入初始标准输入
后会关闭输入管道。独立 `pause` 与集成测试中的受控 CMD 均验证了该行为。

参考打包工具依赖 Python 与 PowerShell。单看 CMD 的退出码不足以证明打包全部
成功。插件核验本次 HEX/签名内容、profile 引用与镜像、App 来源、CBF 归档及大文件
split 分片，检查通过才进入 SDK 阶段。原始工程 CMD 的内部逻辑和既有产物更新方式
不被改写。运行脚本前应确保其依赖的 Python、PowerShell 及工具已安装。

## 运行与结果

1. 在 GUI 或 TUI 的能力设备配置中指定 EXE。插件固定连接本机 SDK 地址
   `ws://localhost:8777`，不提供地址配置，也不修改服务端监听配置。
2. 手动关闭 VCarDAS 的旧工程，可保留空窗口。插件会核对 PID、EXE 路径和启动时间，
   并只读检查可见的空白启动页；兼容提供传统工程菜单命令的版本时，也接受“关闭工程”
   命令禁用且“打开工程”命令启用。无法取得任一种证据时拒绝执行。`Ready` 或空测试树
   不会被当成旧工程已关闭的证据。
3. 创建任务并提供 ZIP、App 与 Driver 文件。插件只修改解压后的工程副本布局，打开工程后
   通过 `TestSetupOpen` 打开「测试配置」页面，按本次目标名称删除原有 CAPL/XML 模块，再在
   原 `Test Environment` 中创建模块。其他名称的模块、环境、文件夹和其他环境的
   勾选状态保持不变，ZIP 工程内容也不修改。
   工程数据和后台预解析仍按 VCarDAS 自身流程加载。
4. 所有目标完成打包校验后，取得固定目录独占
   锁并加载刷写数据。同一台机器不能并行运行本插件的固定目录操作。
5. 查看逐目标打包、配置编译、单轮执行阶段。其他模块取消选择，任一目标失败即停止
   后续目标；未执行目标保持未执行状态。单任务最多 331 个目标，以满足工作流阶段上限。
6. 在测试详情中查看各目标状态，在执行详情中查看发布的产物：执行计划、固定目录
   加载记录、工具身份、打包 stdout/stderr 与校验记录、编译诊断、模块结果及可用报告。
7. 正常、取消或异常均进入收尾：重新核验进程，停止本轮模块和测量，连续两次确认
   实验销毁后请求退出。收尾失败会明确记入任务与 `cleanup.json`，不能当成正常结束。

打包阶段每目标 390 秒，配置编译每目标 780 秒，执行每目标 2280 秒；模块测试默认
最多 30 分钟，终态后独立等待报告 60 秒。报告尚未就绪、不可用或生成失败会告警，
不会拿上一轮报告替代；报告复制失败属于任务错误。任务总时限还应覆盖所有目标。

## 验证

GUI 与 TUI 使用同一清单、阶段、结果树和执行后端。专项回归覆盖输入计划、SDK
会话异常、固定目录和 CMD 产物校验、完整工作流，以及 TUI 配置和结果展示：

```sh
ctest --preset=dev-windows-local -R '^AtechCICTPilot_((tui_)?vcardas_bootloader|vcardas_native)$'
```

本机辅助脚本和完整工作流测试仅在 Windows 执行，固定目录被测试夹具隔离到临时目录。
测试不启动真实 VCarDAS、不访问刷写设备；GUI 视觉效果和真实台架流程由现场验收。
