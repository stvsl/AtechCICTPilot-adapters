# VCarDAS BOOT 刷写插件实现方案

## 已确认的业务流程

1. 设备配置选择 `VCarDAS2.exe`；任务加载工程 ZIP 和多组 App、Driver 文件。
2. App 每目标一组同名 `.hex/.cbf + .rsa`，Driver 每目标一组同名 `.hex + .rsa`。
3. 依据固件主名的连续前缀匹配工程目标目录；目标数由输入决定，不限定 FL。
4. 在工程工作副本内替换匹配目标 `APP`、`Flashdriver` 中的刷写输入，运行该目标
   随工程提供的 `put_pkg.cmd`，由脚本从工程内的同级 `tools` 加载打包依赖。
5. 所有目标打包通过后，将校验过的刷写数据加载到 `D:\KUNYI_flash\<目标名>\`，
   供原样运行的 CAPL 读取。
6. 使用设备配置指定的 VCarDAS，打开 ZIP 中同一个 `.das` 的任务副本。旧工程由
   用户先手动处理，插件不自动保存或关闭旧工程，不再要求并行新建实例。
7. 打开「测试配置」后，删除名称与本次刷写目标相同的旧 CAPL/XML 模块，再为本次刷写目标配置模块。
   清理会检查整棵配置树，但只删除同名模块，保留其他测试项和工程环境结构。
8. 在目标的 `capl` 下找以目标名开头的 `.can`，在 `DLL` 下找包含目标名的
   `.dll`，配置给新模块并编译。
9. 执行匹配到的全部模块，收集结果及可用报告，在任务页面展示各目标结论。

多个目标按目录名排序串行执行，任一目标失败即停止后续执行。所有本次刷写模块放在
原有的 `Test Environment` 测试环境下面。
每个匹配模块的全部可用用例只执行一轮，其他模块取消勾选。

工程解压为任务工作副本，任务输入中的原工程文件不被修改。SDK 的 `CloseProject`
会保存旧工程后关闭；用户已明确选择由自己先处理旧工程，插件不能自动执行该动作。
用户先关闭旧工程，保留的空窗口用于打开本次工程；软件未运行时启动指定 EXE。
本次执行结束后关闭软件。

`D:\KUNYI_flash\` 在任务结束后保留加载后的数据、打包产物及可用结果，不做目录
整体删除或回滚。任务页面同时保留执行计划、打包日志、编译诊断、模块结果和可用
测试报告。脚本本身的既有产物更新行为保持原样。

文件无匹配、前缀多重匹配、多个 CAPL/DLL 候选统一报错，不自动选择。
开始加载前先校验全部目标，避免部分输入被忽略。

## 实现分工

- `PackageInfo.json`：输入格式、设备 exe 字段和 CLI/WebSocket 权限。
- `scripts/vcardas/project.js`：输入名称恢复、固件成组校验、工程目标及文件发现。
- `scripts/vcardas/native.js` / `native.ps1`：固定目录独占、加载、原 CMD 调用、产物检查和报告复制。
- `scripts/vcardas/rpc.js` / `session.js`：串行 RPC、进程归属与工程、模块和测量生命周期。
- `scripts/entry.js` 与 `StepConfig.groovy`：准备、启动、模块配置、执行、结果与收尾。
- 共用的宿主任务结果接口向 GUI/TUI 提供同一数据，不分别维护界面业务状态。

通过现有运行时接口实现，不引入针对 VCarDAS 的宿主 C++ 专用接口。
使用 SDK 相同的本机 WebSocket 协议，避免仅为 RPC 传输捆绑另一套 Python 依赖。
固定目录超出 `@atech/fs` 的任务 URI 范围，应通过 CLI 白名单允许的本机辅助脚本
处理，不向文件系统接口传入绝对路径以绕过 URI 边界。

## 分阶段执行设计

| 阶段 | 操作与完成条件 |
| --- | --- |
| 校验与计划 | 解压 ZIP；先完整校验所有成组文件、目标、CAPL、DLL 和打包脚本；只为任务工程副本写入单页布局并清理旧停靠布局；发布目标清单 |
| 准备打包输入 | 清理工程工作副本中各匹配目标的旧固件输入，复制本次两组文件 |
| 打包 | 按目标名顺序在各目标的工程工作副本内运行随附的 `put_pkg.cmd`，保留日志并核验 CAPL 所需输出 |
| 固定目录加载 | 取得独占锁，将本轮已校验的刷写数据复制到 CAPL 读取目录 |
| 工具连接或启动 | 用户先手动关闭旧工程；复用保留的空窗口，无实例时启动指定 EXE；核对 `ApplicationStatus.ProcessId`、程序路径和 Ready 后打开工程副本，并调用 `TestSetupOpen` 显示唯一的「测试配置」页面 |
| 配置与编译 | 校验唯一 `Test Environment` 并预读整棵配置树；仅删除全树中名称与本次目标相同的 CAPL/XML 模块；核验其他配置保留后在原环境创建模块、配置 CAPL/DLL 并检查编译诊断 |
| 串行执行 | 显式取消其他模块勾选，选中本次目标及其全部可用用例；启动测量，按目标名逐个执行一轮，首个失败即停止 |
| 结果与收尾 | 收集本轮 RunId 对应结果和报告，反馈共用 GUI/TUI 后端；停止测量并等待实验销毁，关闭执行本次任务的软件，保留固定目录数据 |

阶段时限与每个目标的动态执行阶段由工作流明确设置；取消、超时和异常均进入收尾。
工程中的旧循环次数不能带入新模块，本次执行须验证每个模块只启动一次。

只有核验工具进程身份后的连接才能发出工程修改、测量或退出指令。新启动的进程需
核对实际启动 PID；复用已有实例需核对服务端 PID 的程序路径与所选 EXE 一致。
身份不符时立即停止，不能通过该连接调用 `ExitApplication`。

## SDK 对照

参考 SDK：`TestModuleSDKApps/DasPythonSDK` 的 `使用文档.md`、`sdk/` 和
`examples/sdk_example_testmodule.py`。适配器固定连接服务端
`ws://localhost:8777`，不向 GUI、TUI 或任务输入暴露地址配置。

| 操作 | SDK 协议方法 | 需要检查的结果 |
| --- | --- | --- |
| 启动工具 | 本机 `VCarDAS2.exe --unattended` | 进程存活；服务端 PID 与本次启动 PID 一致；Ready |
| 打开工程 | `OpenProject` | 外层 Success、Result、警告 |
| 打开测试配置 | `TestSetupOpen` | `OpenProject` 成功后请求唯一的测试配置页面；工程副本布局没有其他子窗口 |
| 查询配置 | `TestSetupTree` | 节点 Id、Name、Type、父子关系 |
| 删除旧测试模块 | `TestSetupDelete` | 逐个按节点真实 ID 删除全树内与目标同名的 CAPL/XML 模块；SDK 同步清理模块注册；保留其他测试项并重新查询验证 |
| 创建模块 | `TestSetupInsertModule` | 明确父环境 ID，使用返回的新节点 ID |
| 配置脚本与库 | `TestModuleConfigure` | 使用本机存在的绝对路径 |
| 等待空闲 | `BackgroundWaitIdle` | 编译前后台任务已空闲 |
| 编译模块 | `TestModuleCompile` | 外层 Success 和返回对象内层 Success；保留 Diagnostics |
| 模块与用例选择 | `TestSetupSetActive`、`TestModuleSetCaseActive` | 执行范围需要显式确定 |
| 校验用例范围 | `TestModuleCases` | `Children` 为 `null` 或空数组表示叶子，部分勾选的组可返回 `IsActive: null`；核对可用叶子已勾选并记录单轮总数 |
| 测量开始与停止 | `Start`、`Stop`、`Running` | 执行模块前需要启动测量 |
| 控制模块 | `TestModuleControl` | 返回表示进入目标状态，不表示测试完成 |
| 查询结果 | `TestModuleProgress` | 绑定本轮 RunId，等待 IsFinal/Result；独立等待报告 |
| 等待实验销毁 | `DeviceExperimentDestroyStatus` | 停测后连续两次 Destroyed；其他状态不能当成功 |

RPC 无请求 ID，同一连接必须串行调用。请求超时、取消或响应损坏后废弃连接，避免
迟到响应被当作后续请求的结果。删除、创建、编译、开始执行等有副作用的请求不自动
重试。旧的报告路径可能属于上一轮，必须使用本轮 RunId 的进度快照。

## 与参考 CANoe 适配器的关系

借鉴其 ZIP 工作副本、分阶段日志、执行超时、结果/报告收集和失败收尾组织方式。
VCarDAS 使用 SDK 的 WebSocket 协议、动态创建同名模块及工程内的 `put_pkg.cmd`，
这些差异不能直接套用 CANoe 的 Automation 和刷写契约。

## 实例模式与 SDK 约束

用户已明确要求不修改 VCarDAS 用户共享配置，不以并行新建实例作为实施前提。
旧工程由用户先手动处理，插件不自动保存或关闭。任务输入中的 `.das` 仍使用工作
副本，本次测试完成后关闭执行任务的软件。

用户确认执行顺序为“先关闭旧工程，然后打开新的工程”。插件复用保留的空窗口；
软件未运行时启动指定 EXE，不强制用户退出已留空的软件。

`ApplicationStatus.Ready` 仅表示主窗口已加载，不表示旧工程已经关闭。SDK 没有在
该状态中提供当前工程路径，不能将 Ready 或测试配置树为空当成没有旧工程的证明。
旧工程须由用户先关闭；旧工程状态检查的具体方式需在 SDK 联调时验证。任何检测到
旧工程或无法确认目标实例的情况都应在打开任务工程前报错，不能自动保存 / 关闭。

以下是已完成的只读调研摘要，完整证据见[SDK 与实例调研](sdk-research.md)。

2026-11-16 对提供的 `Das2App_SDK_1111` 做只读检查，发现：

- `VCarDAS2.StartupArguments.Parse` 识别 `--unattended` 和工程路径，没有发现
  启动端口参数。
- `Gemini.AppBootstrapper.StartRemoteServices` 从
  `ConfigHelper.LoadConfig().RemoteUrl` 读取监听地址；未配置时默认
  `ws://localhost:8777`。
- 配置位于 Windows“文档”目录下的 `VCARSYSTEM\VCARDAS2\config.json`，属于
  当前用户的共享配置，并非所选 EXE 目录下的独立配置。
- SDK 构造参数 `port` 和示例的 `--port` 只设置客户端连接地址，不控制服务端
  监听端口；`application.start()` 会在所连端口已有会话时拒绝启动。
- 随附的中英文手册，以及核查到的官网公开产品资料，没有找到符合上述约束的
  多实例启动命令或独立配置说明。手册提及的 Trace 等窗口“多开”不是进程多实例。

当前未取得厂商多实例方式，不能将资料中未找到启动方式解释为软件不支持多实例。
上述为方案选择前的只读调研记录，不作为现行实现的阻塞条件。

固定目录、文件匹配、模块范围和失败停止等已确认业务规则继续有效。

当前准备阶段要求 ZIP 内 `.das` 唯一，多个文件会报错，不自动选择。插件仅删除工程测试树
中名称与本次目标相同的 CAPL/XML 节点，包括位于其他环境中的同名节点；不删除环境、文件夹
或其他名称的测试项，也不会更改其他环境的勾选状态；ZIP 中的原始工程文件不受影响。

## 当前实现边界

上述工作流已实现。每目标生成打包、配置编译、执行三个动态阶段，分别设置
390/780/2280 秒时限；共享阶段完成计划、进程核验、配置范围校验、汇总和收尾。
单任务限制为 331 个目标，避免超出宿主的 1000 个主阶段上限。任务总时限需要按
目标数量设置。编译诊断、打包日志、本轮 RunId 快照与可用报告均登记到任务产物。

进程核验通过后，以 Windows UI Automation 只读检查空白启动页；兼容提供传统工程
菜单命令的版本时，也接受“关闭工程”禁用且“打开工程”启用。两种证据均要求对应
控件可访问，启动页标记还必须实际可见。该检测采用保守拒绝策略；无法读取时不会退回
以 Ready、空测试树或用户声明代替检查，也不会保存或关闭旧工程。

GUI/TUI 共用 `task.reportResult` 的目标汇总和 `@atech/task/case` 的结果树，
未执行目标不计为通过。固定目录和报告复制经白名单 PowerShell 辅助脚本完成，
未增加宿主专用 API。全局互斥锁在任务存续期间持有，退出后保留目录数据。

已补充验证 CMD 的 `pause`：宿主 CLI 会关闭标准输入，独立 `pause` 命令通过空输入
管道运行时立即返回，因此不需要为跳过等待按键而修改工程脚本。

## 当前验证结果

自动回归分为以下层次，具体运行命令见[使用说明](usage.md)：

- 真实 QuickJS 的固件分组、目标发现、任务快照名称、全目标校验、任务工程副本的单页布局及源工程保护。
- SDK 会话场景：成功与启动、错误路径/PID、旧工程、拒绝打开或测试配置页、跨环境删除同名 CAPL/XML 模块并保留其他节点、编译失败、
  重复轮次、RunId 替换或不更新、RPC 超时/损坏/二进制、取消、报告不可用、实验
  销毁未知及收尾身份变化。使用虚拟时钟和受控 RPC 响应验证异常分支。
- Windows 本机脚本：在临时根目录验证工程随附 CMD 及相对路径依赖、缺少工程脚本时
  报错、产物缺失拒绝、签名全量预校验、报告资源复制与互斥锁异常释放。
- 完整工作流：真实 PluginExecutionThread、QuickJS、CLI、PowerShell、CMD 和本机
  WebSocket 服务串联，覆盖双目标成功、首目标失败停止及运行中取消；只替代软件
  窗口证明和进程退出，不使用真实 VCarDAS 或刷写设备。
- TUI：清单驱动的 EXE/SDK 地址配置、两类多文件输入、必填校验、动态阶段、目标
  状态及报告产物展示。

另将提供的参考工程原版 `put_pkg.cmd`、profile 和配套工具放入临时目录，使用合成
HEX 与签名输入验证了实际 CMD 的打包与产物检查；该验证不操作 VCarDAS 或设备。

真实固件（尤其 CBF 转换）、VCarDAS 空窗口菜单识别、CAPL 编译、硬件测量与刷写
仍需现场验证。自动回归不能替代这些验收；GUI 视觉和交互验证交由用户反馈。
